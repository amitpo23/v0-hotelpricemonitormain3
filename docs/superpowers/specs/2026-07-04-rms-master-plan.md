## 1. העיקרון המארגן

מערכת ניהול תשואה (RMS) אמיתית היא **לולאת בקרה** שרצה ללא הפסקה, לכל מלון בנפרד:

```
חישה (Sense) → חיזוי (Forecast) → אופטימיזציה (Optimize) → פעולה (Act) → למידה (Learn)
   מצב המלון        ביקוש צפוי         המחיר שממקסם          דחיפת מחיר      חיזוי מול
   מול מצב השוק     לכל תאריך          RevPAR בהינתן         לערוצי המכירה   תוצאה בפועל
                                       מלאי וזמן שנותר
```

כל החלטת מחיר = **מצב המלון** (מלאי שנותר, קצב הזמנות, אילוצים) × **מצב השוק** (מתחרים, ביקוש, אירועים) × **אסטרטגיה** (מיצוב, גמישות מחיר). היום למערכת יש רק את צד השוק.

## 2. עמוד השדרה הארכיטקטוני החדש: Integration Hub

בגלל הכרעות 1–2, הלב של המערכת הוא שכבת מתאמים אחידה. כל מלון (tenant) מגדיר בקונפיגורציה אילו מתאמים פעילים עבורו:

```

│                                                                                       │
│   OccupancySource        RateShopSource         PricePusher          DemandSignal     │
│   (תפוסה/מלאי/הזמנות)    (מחירי מתחרים)         (דחיפת מחירים)       (אותות ביקוש)    │
└───────┬──────────────────────┬──────────────────────┬──────────────────────┬──────────┘
        │                      │                      │                      │
  ┌─────┴─────┐          ┌─────┴─────┐          ┌─────┴─────┐          ┌─────┴─────┐
  │ מתאמים:   │          │ מתאמים:   │          │ מתאמים:   │          │ מתאמים:   │
  │ Medici    │          │ Apify     │          │ Channex   │          │ אירועים   │
  │ Monitor   │          │ Booking   │          │ Beds24    │          │ חגים      │
  │ ייבוא     │          │ Scraper   │          │ Zenith    │          │ מזג אוויר │
  │ Excel/CSV │          │ Engine    │          │ Advisory  │          │ למ"ס      │
  │ PMS APIs  │          │ (עצמאי)   │          │ (המלצה    │          │ חדשות     │
  │ (Cloudbeds│          │           │          │  בלבד)    │          │ טיסות     │
  │  Mews...) │          │           │          │           │          │           │
  └───────────┘          └───────────┘          └───────────┘          └───────────┘
```

**עקרונות:**
- ממשק TypeScript אחיד לכל קטגוריה (`lib/integrations/contracts.ts`); כל מתאם = מודול שמממש את הממשק + רשומת קונפיג ב-DB (`hotel_integrations`: hotel_id, type, provider, credentials מוצפנים, status)
- **לכל קטגוריה יש מתאם אוניברסלי שעובד תמיד:** תפוסה — ייבוא Excel/CSV ידני (קיים חלקית: `/api/bookings/import-pms`); דחיפת מחירים — מצב Advisory (המלצה + אישור ידני); כך מלון בלי אף API עדיין מקבל ערך מלא מהמערכת
- נכסי Medici הקיימים הופכים ל**מתאמים הראשונים** (reference implementations), לא לתלות קשיחה
- **Channex.io כמתאם אסטרטגי לדחיפת מחירים:** API אחד שמכסה 200+ ערוצים (כולל Booking.com) — פותר את בעיית ה"כל מלון עם channel manager אחר" עבור רוב המלונות

## 3. מצב המוצא (ממצאי המחקר — מאומתים בקוד)

### מה עובד
- מנוע חיזוי פקטוריאלי אמיתי (`lib/prediction-algorithms.ts`) + Decision Agent + Ensemble + Feedback Loop (קוד אמיתי, "מורעב" מדאטה)
- 8/10 סוכנים עם מקורות דאטה אמיתיים; אורקסטרציה עם circuit breakers
- 68 API routes, ~40 דפי UI דו-לשוניים; רוב הטבלאות כבר עם `hotel_id` (בסיס טוב לרב־מלונאות)

### מה שבור (Top 6, לפי חומרה)
1. **סקרייפינג שבור בפרודקשן** — `scrapeViaPlaywright` לא מוגדר; נתיב פייתון קשיח של Codespaces; 3 Apify actors שונים; ב-Vercel רק Tavily (regex על טקסט) עובד בפועל
2. **אפס הרשאות צד-שרת** — middleware מאשר הכול; `/api/autopilot/execute` משנה מחירים ללא auth; `/api/debug/hotel-data` דולף דאטה; אין RLS — חוסם רב־מלונאות
3. **צינור הדאטה לא זורם** — `competitor_price_history`, `daily_prices`, `price_predictions` לא מתמלאים אוטומטית ⇒ הלמידה לא לומדת
4. **שני סוכנים מפוברקים** — CBS Tourism ו-News Sentiment מזרימים דאטה מומצא להחלטות מחיר
5. **דיפלוי שבור מאז 10.2.2026** — `ERR_PNPM_OUTDATED_LOCKFILE`; crons רק ב-Vercel אבל הסקרייפר רק ב-Railway
6. **DB לא משוחזר** — ~16 טבלאות חיות ללא מיגרציות, 28 תלויות "latest", שני lockfiles

### שלב 1: יסודות רב־מלונאיים + Integration Hub (שבוע 1–2)
- **1א. מודל Tenancy:** ארגון ⇒ משתמשים ⇒ מלונות (`hotel_user_access` קיים — להשלים); **RLS על כל טבלה לפי hotel_id**; כל שאילתה ב-API עוברת דרך scope של המלון
- **1ב. חוזי האינטגרציה:** `lib/integrations/contracts.ts` — ארבעה ממשקים (OccupancySource, RateShopSource, PricePusher, DemandSignal) + טבלת `hotel_integrations` (credentials מוצפנים) + UI הגדרת חיבורים לכל מלון
- **1ג. מתאמי חובה (האוניברסליים):**
  - תפוסה: ייבוא Excel/CSV משופר (על בסיס `/api/bookings/import-pms` הקיים) + הזנה ידנית ב-UI
  - Rate shopping: Apify actor יחיד (`voyager/booking-scraper`) מ-Vercel; מחיקת 3 הנתיבים המתים
  - דחיפת מחירים: מצב Advisory (המלצות בלבד)
- **1ד. מתאמי Medici (הראשונים האמיתיים):** medici-monitor (תפוסה+P&L), medici-backend (הזמנות ⇒ Pickup/Pace)
- **1ה. החלפת הסוכנים המפוברקים:** למ"ס אמיתי (data.gov.il), NewsAPI אמיתי; עד אז משקל 0
- **1ו. שרשור הצינור:** cron יחיד לכל מלון: scan ⇒ history ⇒ daily_prices ⇒ חיזוי ⇒ prediction_logs
- **1ז. לולאת Diff רציפה:** כל סריקה משווה למצב הקודם; שינוי מהותי (מתחרה שינה מחיר >X%, מלאי מתחרה נסגר לתאריך, אירוע חדש) ⇒ התראה + חישוב מחדש מיידי של ההמלצה לתאריכים המושפעים (לא מחכים לסבב הלילי). טבלת `market_changes` + סף רגישות פר-מלון
- **קריטריון הצלחה:** שני מלונות (אחד Medici, אחד "ידני" עם Excel) רצים במקביל 7 ימים עם דאטה יומי מלא, מבודדים זה מזה ב-RLS

### שלב 2: חיזוי — איחוד המוחות (שבוע 3–4)
- **מנוע עונתיות ו-YoY פר-מלון** — פרופיל "מתי עולה ומתי יורד" משלושה מקורות לפי זמינות: (א) היסטוריית מחירים/הזמנות רב-שנתית של המלון עצמו (למלונות Medici — backfill מ-Azure SQL SalesOffice); (ב) היסטוריית מתחרים הנצברת מהסריקות; (ג) Bootstrap לשוק: תפוסה חודשית עירונית מהלמ"ס + לוח חגים/אירועים — כך שגם מלון חדש מקבל עקומת עונתיות מהיום הראשון. הפרופיל מוזרם לפקטור העונתיות של המנוע הקיים במקום הקבועים של היום
- לקוח TS ל-`medici-prediction-api` (לפי INTEGRATION_SPEC) כספק חיזוי ב-Ensemble
- Ensemble משקלל: מודל פקטוריאלי מקומי + מוח חיצוני + SMA/YoY, משקולות נלמדות פר-מלון
- השלמת הפיצ'רים החלולים ב-`feature-engineering.ts`
- הפעלת לולאת דיוק על דאטה אמיתי; דוח MAPE שבועי פר-מלון
- **קריטריון הצלחה:** MAPE נמדד (לא מוצהר) על 30 יום; baseline מתועד

### שלב 3: אופטימיזציה — מהחיזוי למחיר (שבוע 5–6)
- פורט `price-elasticity-service` + `revenue-maximization-service` ל-TS
- תמחור מודע-מלאי פר סוג חדר: מחיר = f(תחזית ביקוש, חדרים שנותרו, ימים לצ'ק-אין, מיצוב מול comp-set)
- מעקות בטיחות הצהרתיים ב-DB פר-מלון: רצפה/תקרה לפי סוג חדר ועונה, מקס' שינוי יומי %, סף ביטחון
- **קריטריון הצלחה:** לכל תאריך ב-90 ימים קדימה — המלצת מחיר + הסבר + ציון ביטחון, מתעדכן יומית

### שלב 4: פעולה — סגירת הלולאה (שבוע 7–8)
- **מתאם Channex.io** כ-PricePusher ראשי (API אחד ⇒ Booking.com ועוד 200+ ערוצים) + מתאם Zenith למלונות Medici + מצב Advisory כברירת מחדל
- שלושה מצבי Autopilot פר-מלון, עלייה מדורגת: **Shadow** (רישום בלבד, שבועיים מינ') ⇒ **Approval** (אישור בקליק, UI + Telegram) ⇒ **Auto** (בתוך המעקות, עם rollback)
- Audit log מלא לכל שינוי
- **קריטריון הצלחה:** שינוי מחיר שאושר מופיע בערוץ המכירה בפועל

### שלב 5: למידה (שבוע 9–10)
- השוואה יומית: חיזוי מול בפועל (מחיר, תפוסה, השפעת שינויים על Pickup)
- עדכון משקולות אוטומטי פר-מלון (`weight-optimizer.ts` קיים) על דאטה אמיתי
- דוח שבועי אוטומטי פר-מלון: RevPAR, ADR, דיוק, החלטות Autopilot — Telegram/מייל
- **קריטריון הצלחה:** שיפור MAPE מדיד בין חודש 1 לחודש 2

### שלב 6: קוקפיט ותפעול (שבוע 11–12)
- דשבורד אחד פר-מלון: לוח שנה עם חום-ביקוש; לכל תאריך — מתחרים, Pickup, תחזית, המלצה, סטטוס פעולה
- מסך ניהול אינטגרציות (חיבור/ניתוק מתאמים, בריאות חיבורים)
- התראות: מתחרה ירד >10%, קצב חריג, אירוע חדש, מתאם שנפל
- ניקוי ~40 דפים ⇒ 6-8 מסכים חיים
- **קריטריון הצלחה:** onboarding מלון חדש מקצה-לקצה בפחות משעה, בלי לגעת בקוד
